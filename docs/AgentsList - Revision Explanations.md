**بله، فهرست نیاز به بازبینی دارد.** مشکل اصلی تعداد نیست، تعریف «agent» است. از حدود ۵۰ مورد، بیشتر آنها در عمل تابع قطعی، بخشی از یک پرامپت، قابلیت آماده‌ی LangGraph یا زیرساخت‌اند و agent مستقل لازم ندارند.

## مشکلات فهرست فعلی

**۱. هر مورد یک فراخوانی LLM نیست.** روی مدل محلی هر فراخوانی چند ثانیه طول می‌کشد. زنجیره‌ی ۱۰ تا ۱۵ مرحله‌ی LLM یعنی پاسخ‌دهی در حد دقیقه، خطای انباشته و دیباگ سخت. Embedding، Fusion، Sparse Retriever، Logging و Session Context به LLM نیاز ندارند.

**۲. هم‌پوشانی زیاد.** این گروه‌ها را می‌توان ادغام کرد:
- Normalizer، Rewriter، Expansion و HyDE همگی مرحله‌ی «آماده‌سازی کوئری» هستند.
- Intent، Language/Domain و Router را می‌توان در یک فراخوانی با خروجی ساختاریافته (JSON) انجام داد.
- Embedding، Dense، Sparse و Fusion یک گره‌ی جستجوی هیبرید هستند.
- ERP Specialist و Product Docs Specialist یک generator با دو پرامپت و دو ایندکس‌اند، نه دو agent.
- Answer Generator، Reasoning، Summarizer، Tone، Grammar و Formatting را یک پرامپت خوب و مدل مناسب پوشش می‌دهد.
- Relevance Grader و Query Retry یک حلقه‌ی واحد (Corrective RAG) هستند.
- Short-Term و Session Context همان checkpointer در LangGraph‌اند.

**۳. ایمنی نباید به LLM سپرده شود.** Permission Agent و بخش مهم Guardrail باید کد قطعی باشند. بهترین نقطه‌ی اعمال دسترسی خود بازیابی است: فیلتر ACL روی متادیتای chunkها، تا سند غیرمجاز اصلاً به context نرسد. Business Rule هم باید کد قطعی باشد، نه تصمیم مدل.

**۴. لایه‌ی ERP پرریسک‌ترین بخش است.** Action Executor (نوشتن در ERP) را باید در مراحل بعد و با تأیید انسانی، idempotency و ثبت کامل لاگ اضافه کرد. Data Lookup بهتر است ابزار با API از پیش تعریف‌شده و فقط‌خواندنی باشد، نه text-to-SQL آزاد.

**۵. چند مورد حیاتی جا افتاده‌اند** (بخش آخر را ببینید).

## اولویت‌بندی بر پایه‌ی ضرورت و هزینه به فایده

«هزینه» یعنی پیچیدگی پیاده‌سازی به‌علاوه‌ی تأخیر اجرا.

### اولویت ۱: هسته‌ی MVP (حتماً)

| مورد | نوع | هزینه | فایده | توضیح |
|---|---|---|---|---|
| Ingestion و Chunking (جاافتاده) | زیرساخت | متوسط | بسیار بالا | کیفیت RAG بیش از هر agent به این مرحله وابسته است |
| Query Normalizer | تابع قطعی | بسیار کم | بالا | یکسان‌سازی ی/ک عربی، نیم‌فاصله، ارقام و فاصله‌گذاری. بدون LLM |
| Hybrid Retrieval (Dense + BM25 + RRF) | گره واحد | کم | بسیار بالا | در ERP اصطلاحات دقیق و کد منو زیاد است و BM25 اینجا ارزشمند است |
| Reranker (Cross-Encoder) | مدل محلی | کم | بالا | بیشترین بهبود دقت به ازای کمترین تلاش |
| Answer Generator (شامل استدلال، لحن و قالب) | یک LLM | کم | بسیار بالا | با پرامپت جدا برای هر دامنه |
| Citation | قطعی | کم | بالا | از شناسه و متادیتای chunk ساخته می‌شود، نه از حافظه‌ی مدل |
| Short-Term Memory | checkpointer | کم | بالا | قابلیت آماده‌ی LangGraph |
| Permission (فیلتر ACL) و Guardrail پایه | قطعی | متوسط | بسیار بالا | در ERP غیرقابل مذاکره است |
| Fallback (شامل «نمی‌دانم») | edge شرطی | کم | بالا | پرهیز از جواب ساختگی |
| Logging و Tracing | ابزار | کم | بالا | مثلاً Langfuse یا LangSmith نسخه‌ی self-hosted |
| Evaluation (آفلاین) | اسکریپت | متوسط | بسیار بالا | با مجموعه‌ی طلایی ۵۰ تا ۱۰۰ پرسش واقعی، از همان ابتدا |

### اولویت ۲: ارتقای کیفیت (بعد از MVP)

| مورد | هزینه | فایده | توضیح |
|---|---|---|---|
| Router/Intent (یک فراخوانی ادغام‌شده) | متوسط | بالا | وقتی ابزار و عملیات اضافه شود ضروری است. پرسش اطلاعاتی را از درخواست عملیات جدا می‌کند |
| History-aware Query Rewriter | کم | بالا | برای پرسش‌های پیگیری مثل «و برای انبار دوم؟» در چت حیاتی است |
| Relevance Grader و یک Retry | متوسط | متوسط تا بالا | نسخه‌ی ارزان: آستانه روی امتیاز reranker. LLM-grader فقط اگر آن کافی نبود |
| Data Lookup (فقط‌خواندنی) | متوسط | بالا | داده‌ی زنده‌ی ERP مثل وضعیت فاکتور، با ابزار و RBAC |
| PII Filter | کم | متوسط تا بالا | regex و قواعد، نه LLM |
| Feedback Collector | کم | بالا | دکمه‌ی 👍/👎 و ذخیره‌ی علت. خوراک بهبود مداوم است |

| Hallucination Checker | زیاد | متوسط | روی مدل محلی گران است. ابتدا با «پاسخ فقط از context و با ارجاع اجباری» شروع کنید و بررسی کامل را برای سناریوهای پرریسک نگه دارید |
| فرهنگ اصطلاحات ERP (جایگزین Query Expansion با LLM) | کم | بالا | فهرست مترادف فارسی/انگلیسی («فاکتور = invoice») به‌صورت قطعی |

### اولویت ۳: مشروط به نیاز واقعی

| مورد | چه زمانی؟ |
|---|---|
| Tool-Calling Agent کامل | وقتی بیش از دو یا سه ابزار دارید |
| Supervisor | وقتی چند زیرگراف مستقل دارید. پیش از آن یک گراف با Router ساده کافی است |
| Human-in-the-Loop، Action Executor، Business Rule | در فاز عملیات نوشتنی. HITL با `interrupt` در LangGraph ارزان است، ولی ریسک بالاست |
| Long-Term Memory | فقط برای ترجیحات پایدار کاربر، و با رضایت و سیاست نگهداری روشن |
| Reasoning Agent جدا | فقط برای پرسش‌های چندمرحله‌ای واقعی (مثلاً محاسبه یا مقایسه‌ی چند سند) |
| Context Compressor | اگر context window کوچک است یا chunkها بلندند |
| HyDE | فقط اگر ارزیابی نشان داد recall پایین است. روی دامنه‌ی تخصصی فارسی ممکن است نویز اضافه کند |
| Summarizer | فقط برای خلاصه‌ی تاریخچه‌ی گفتگوی بلند |

### اولویت ۴: حذف یا ادغام (agent مستقل نشود)

Embedding Agent، Sparse Retriever، Hybrid Fusion، Language & Domain Detector، Query Retry، ERP/Product Specialist، Grammar Corrector، Tone & Style، Formatting، Consistency Agent، Session Context، و نسخه‌ی agent از Logging و Evaluation. هرکدام را به یکی از دسته‌های بالا منتقل کنید. Consistency Agent هزینه‌ی زیاد و فایده‌ی کم دارد و بهتر است حذف شود.

## مواردی که در فهرست نیست و باید اضافه شود

- **ACL در سطح سند و chunk**، و جداسازی ایندکس بین ماژول‌ها، نقش‌ها و در صورت لزوم tenantها.
- **نسخه‌گذاری و تازه‌سازی ایندکس** (incremental indexing)، چون مستندات ERP با هر نسخه تغییر می‌کند. متادیتای «ماژول/نسخه‌ی محصول» برای هر chunk لازم است.
- **انتخاب مدل embedding و reranker چندزبانه** و محک‌زدن روی داده‌ی فارسی خودتان (مثلاً خانواده‌ی bge-m3 یا multilingual-e5). نتیجه به داده‌ی شما وابسته است، پس عدد مدل را از روی نام انتخاب نکنید.
- **پردازش متن فارسی برای BM25:** نرمال‌سازی نیم‌فاصله و ی/ک، و توکن‌سازی مناسب. متن‌های ترکیبی فارسی/انگلیسی در ERP زیاد است.
- **دفاع در برابر prompt injection از داخل اسناد و داده‌ی ERP**، یعنی محتوای بازیابی‌شده را «داده» بدانید نه «دستور».
- **مسیر تحویل به انسان** (ایجاد تیکت پشتیبانی) برای وقتی که سیستم نمی‌داند یا کاربر ناراضی است.
- **کش** پاسخ و embedding برای کاهش تأخیر روی سخت‌افزار محلی.

## معماری پیشنهادی (حدود ۸ تا ۱۰ گره)

`Normalize ← Router/Intent (+ rewrite با تاریخچه) ← Hybrid Retrieve (با فیلتر ACL) ← Rerank ← [Grade → Retry یک‌بار] ← Generate (+ citation) ← Output Guard (PII/قالب) ← Fallback/Human handoff`

به‌علاوه checkpointer برای حافظه، tracing برای رصد، و یک شاخه‌ی ابزار (Data Lookup فقط‌خواندنی، سپس Action با HITL) که فقط از Router فعال می‌شود.

اگر بخواهید، همین بازبینی را به‌صورت فایل (Word یا Markdown) با جدول کامل نگاشت «هر ۵۰ مورد → سرنوشت نهایی» تحویل می‌دهم.
