# سند مشخصات معماری Multi-Agent
## Multi-Agent Architecture Specification — Version 1.0

**وضعیت سند:** مبنای طراحی و شروع پیاده‌سازی  
**نسخه:** 1.0  
**تاریخ:** 17 نوامبر 2026  
**سامانه:** دستیار هوشمند ERP  
**معماری پایه:** FastAPI Assistant API + Python LangGraph/LangChain Coordinator + Local RAG + Local LLM + External OpenAI API + ERP MCP

---

## 1. هدف سند

این سند معماری هدف دستیار هوشمند ERP را برای حرکت کنترل‌شده از یک Workflow متمرکز به یک سامانه **Selective Hierarchical Multi-Agent** تعریف می‌کند.

هدف، افزایش تعداد Agentها یا تبدیل همه درخواست‌ها به اجرای چندعاملی نیست. هدف، حل بهتر درخواست‌های پیچیده و چندمرحله‌ای است؛ به‌گونه‌ای که سیستم بتواند درخواست را تحلیل کند، وظایف مستقل یا وابسته را مشخص کند، آن‌ها را به Agent تخصصی بسپارد، نتایج را دریافت و ارزیابی کند و پاسخ یکپارچه ارائه دهد.

درخواست‌های ساده باید همچنان از مسیرهای فعلی و کم‌هزینه عبور کنند. Multi-Agent فقط زمانی فعال می‌شود که پیچیدگی درخواست، ارزش استفاده از آن را توجیه کند.

## 2. تصمیم معماری

معماری هدف بر پایه اصول زیر است:

1. **Hierarchical Multi-Agent:** یک Supervisor مرکزی مسئول برنامه‌ریزی، واگذاری و کنترل اجرای وظایف است.
2. **Selective Multi-Agent:** فقط درخواست‌های پیچیده وارد مسیر چندعاملی می‌شوند.
3. **Preserve Existing Workflows:** مسیرهای فعلی Small Talk، RAG ساده و ERP Query ساده حفظ می‌شوند.
4. **Specialized Agents:** هر Agent مسئولیت محدود، ابزارهای مجاز و قرارداد ورودی/خروجی مشخص دارد.
5. **Controlled Delegation:** Agentها آزادانه و بدون کنترل مرکزی به یکدیگر مأموریت نمی‌دهند.
6. **Dependency-aware Execution:** اجرای موازی فقط برای وظایفی مجاز است که وابستگی داده‌ای یا اجرایی ندارند.
7. **Security Outside LLM Authority:** هویت، مجوز، اعتبارسنجی عملیات و تأیید عملیات حساس در لایه قطعی برنامه باقی می‌مانند.
8. **Model Policy Separation:** انتخاب مدل از Orchestration جداست و سیاست فعلی Local LLM/OpenAI تغییر نمی‌کند.
9. **Incremental Delivery:** فاز اول فقط یک Inventory Agent و یک Use Case واقعی را پوشش می‌دهد.
10. **Evidence-based Progress:** عبور از هر فاز به بهبود قابل اندازه‌گیری در کیفیت، سرعت یا قابلیت اطمینان وابسته است.

## 3. معماری موجود و محدوده تغییر

### 3.1 معماری پایه

معماری مبنا برای این سند:

- FastAPI Assistant API به‌عنوان نقطه ورود درخواست‌ها
- Python Coordinator مبتنی بر LangGraph/LangChain
- Local RAG برای بازیابی مستندات
- Local LLM برای مسیرهای محلی
- External OpenAI API طبق Model Policy موجود
- ERP MCP Server برای دسترسی کنترل‌شده به قابلیت‌ها و داده‌های ERP
- Qdrant، PostgreSQL و Redis برای زیرساخت داده و وضعیت
- RabbitMQ در بخش‌هایی که در پیاده‌سازی فعلی برای پردازش ناهمگام استفاده می‌شود
- Terminology/Glossary برای نرمال‌سازی اصطلاحات دامنه، در صورت فعال بودن نسخه مربوطه
- Guardrails، Approval و کنترل‌های موجود برای محدودسازی عملیات

**محدودیت مهم:** این سند جایگزین بررسی کد جاری نیست. پیش از اعمال تغییرات، نام فایل‌ها، قرارداد APIها، State و رفتار واقعی شاخه فعلی باید با نسخه جاری مخزن تطبیق داده شود. هیچ جزء صرفاً براساس نام پیشنهادی این سند نباید دوباره ساخته شود، اگر معادل آن از قبل وجود دارد.

### 3.2 خارج از محدوده این تغییر

موارد زیر در این پروژه معماری، هدف بازطراحی نیستند:

- بازنویسی FastAPI Assistant API
- بازگرداندن .NET به معماری جاری
- جایگزینی ERP MCP با یک لایه Tool اختصاصی جدید
- تغییر سیاست فعلی تولید پاسخ RAG با OpenAI
- بازطراحی احراز هویت و مجوزدهی ERP که در لایه‌های امن فعلی مدیریت می‌شوند
- انتقال همه درخواست‌ها به Multi-Agent
- ایجاد زیرساخت توزیع‌شده Agentها یا Agent-to-Agent messaging در فاز اول
- ایجاد حافظه مستقل و دائمی برای هر Agent در فاز اول

## 4. نمای سطح بالای معماری

### 4.1 مسیر منطقی

```text
User / ERP Client
       |
       v
FastAPI Assistant API
       |
       v
Existing Request Context + Guardrails
       |
       v
Initial Intent / Complexity Decision
       |
       +-------------------- Simple ----------------------+
       |                                                   |
       v                                                   v
Existing Workflow                                  Existing Simple Path
(RAG / Local LLM / ERP MCP)                         (as applicable)
       |
       +-------------------- Complex ---------------------+
                                                           |
                                                           v
                                              Conditional Query Understanding
                                                           |
                                                           v
                                                Supervisor / LangGraph
                                                           |
                                      +--------------------+------------------+
                                      |                    |                  |
                                      v                    v                  v
                                Inventory Agent       Other Agent(s)     Research Agent
                                (Phase 1)             (future)            (future)
                                      |                    |                  |
                                      +--------------------+------------------+
                                                           |
                                                           v

                                                           |
                                                           v

                                                           |
                                                           v
                                                     User Response
```

این نمودار نمای مفهومی است. در فاز اول فقط مسیر Inventory Agent پیاده‌سازی می‌شود. Agentهای آینده در نمودار برای نشان دادن جهت توسعه هستند و به معنی الزام ساخت آن‌ها در نسخه اول نیستند.

### 4.2 اصل مسیر ساده

درخواست‌های ساده نباید صرفاً به دلیل وجود Supervisor از آن عبور کنند. مسیر ساده باید تا حد امکان بدون LLM call اضافی، بدون ساخت Task و بدون اجرای Agent باقی بماند.

نمونه‌های معمول:
- احوال‌پرسی و گفت‌وگوی کوتاه
- سؤال مستنداتی با بازیابی مستقیم
- پرس‌وجوی ساده ERP که با مسیر MCP فعلی پاسخ داده می‌شود

### 4.3 مسیر پیچیده

درخواست‌هایی که چند وظیفه تخصصی، چند منبع داده، تحلیل چندمرحله‌ای یا وابستگی بین مراحل دارند، می‌توانند وارد مسیر Supervisor شوند.

تشخیص پیچیدگی باید با ترکیبی از قواعد و طبقه‌بندی موجود انجام شود. در صورت ناکافی بودن اطلاعات، سیستم باید مسیر امن‌تر را انتخاب کند؛ نه اینکه صرفاً با حدس، اجرای چندعاملی یا عملیات ERP را آغاز کند.

## 5. مسئولیت اجزای اصلی

### 5.1 FastAPI Assistant API

- دریافت درخواست از کلاینت ERP
- اعتبارسنجی ساختار درخواست
- انتقال شناسه‌ها و Context معتبر درخواست به Coordinator
- حفظ قراردادهای API و سازگاری عقب‌رو
- بازگرداندن پاسخ و وضعیت مناسب

این لایه محل تصمیم‌گیری تخصصی Agentها نیست.

### 5.2 Guardrails و Request Context

- اعمال کنترل‌های قطعی موجود
- نگهداری Context معتبر Tenant و User
- اعمال محدودیت‌های مربوط به داده و عملیات
- جلوگیری از عبور درخواست‌های مسدودشده به مراحل بعدی

Guardrail نباید به تصمیم آزاد LLM واگذار شود.

### 5.3 Initial Intent / Complexity Decision

این مؤلفه تعیین می‌کند درخواست می‌تواند از مسیر ساده موجود عبور کند یا نیازمند مسیر پیچیده است.

مسئولیت آن با Query Understanding یکسان نیست:
- Intent/Complexity Decision: انتخاب مسیر اجرایی اولیه
- Query Understanding: استخراج و ساختاردهی معنای درخواست پیچیده

اگر Intent Classifier موجود برای تشخیص پیچیدگی به اطلاعات معنایی بیشتری نیاز داشته باشد، Query Understanding می‌تواند به‌صورت شرطی پیش از تصمیم نهایی اجرا شود. این موضوع باید با ارزیابی Baseline و بررسی کد جاری تعیین شود.

### 5.4 Query Understanding

Query Understanding یک مرحله آماده‌سازی شرطی است، نه Supervisor و نه مجوزدهنده اجرای عملیات.

وظایف:
- استخراج موجودیت‌ها و اصطلاحات
- نرمال‌سازی پرسش
- تشخیص نوع مسئله و وظایف احتمالی
- استخراج فیلترها و بازه‌های زمانی
- شناسایی ابهام‌ها و اطلاعات ناقص
- تولید خلاصه معنایی ساختاریافته

محدودیت‌ها:
- پاسخ نهایی تولید نمی‌کند.
- مسیر اجرایی نهایی را به‌تنهایی انتخاب نمی‌کند.
- Tool فراخوانی نمی‌کند.
- مجوز اجرای عملیات صادر نمی‌کند.
- داده یا شناسه‌ای را جعل نمی‌کند.
- خروجی آن شواهد factual محسوب نمی‌شود.

پیاده‌سازی موجود یا پچ Query Understanding باید پیش از توسعه مجدد بررسی و در صورت تطابق با این مسئولیت حفظ شود.

### 5.5 Supervisor

Supervisor مسئول کنترل جریان درخواست‌های پیچیده است:

- دریافت درخواست ساختاریافته و Context معتبر
- تعیین هدف و شکستن مسئله به Taskهای محدود
- تعیین وابستگی بین Taskها
- انتخاب Agent مجاز
- ارسال Task و دریافت AgentResult
- تشخیص موفقیت، شکست یا کمبود اطلاعات
- تصمیم برای تکمیل، توقف یا درخواست اطلاعات بیشتر
- تحویل نتایج معتبر به مرحله ترکیب پاسخ

Supervisor نباید:
- مجوز کاربر را تولید یا ارتقا دهد.
- محدودیت‌های امنیتی را دور بزند.
- بدون سقف، Task یا Tool call ایجاد کند.
- به‌جای Agent تخصصی، همه منطق دامنه را در خود جای دهد.
- برای درخواست ساده الزاماً اجرا شود.

### 5.6 Domain Agent

Domain Agent مسئول یک حوزه مشخص ERP است. در فاز اول فقط Inventory Agent ساخته می‌شود.

مسئولیت‌های Inventory Agent در Use Case منتخب:
- دریافت Task با هدف روشن و Context محدود
- استفاده از MCP Toolهای مجاز حوزه موجودی
- اجرای مراحل لازم در محدوده Task
- برگرداندن نتیجه ساختاریافته و شواهد
- اعلام صریح نبود داده، ابهام یا خطا

Agent نباید اختیار دسترسی خود را تغییر دهد یا از Tool خارج از محدوده مجاز استفاده کند.

### 5.7 Result Validation و Response Synthesis

در نسخه اول، این بخش می‌تواند در Supervisor یا یک Node محدود انجام شود؛ ساخت Agent مستقل برای آن الزامی نیست.

دو نوع اعتبارسنجی از هم جدا هستند:

**الف) Deterministic Validation**
- تطابق شناسه Task و هویت درخواست
- اعتبار ساختار خروجی
- وجود شواهد مورد انتظار
- کنترل وضعیت Toolها و خطاها
- بررسی سازگاری Tenant/User
- بررسی کامل بودن فیلدهای ضروری

**ب) Semantic Verification**
- آیا شواهد ارائه‌شده از نتیجه‌گیری پشتیبانی می‌کنند؟
- آیا پاسخ از داده‌های بازیابی‌شده فراتر رفته است؟
- آیا تناقض مهمی بین نتایج وجود دارد؟

بخش قطعی باید با کد و قواعد مشخص انجام شود. بررسی معنایی در صورت نیاز می‌تواند با LLM انجام شود و نباید جایگزین کنترل قطعی شود.

Response Synthesis نتایج تأییدشده را به پاسخ منسجم تبدیل می‌کند. پاسخ باید محدودیت‌ها و عدم قطعیت‌های نتایج را حفظ کند.

## 6. قرارداد وظیفه Agent

Task Contract مرز رسمی ارتباط Supervisor و Agent است. قرارداد باید با Pydantic پیاده‌سازی و در زمان اجرا اعتبارسنجی شود.

### 6.1 AgentTask — فیلدهای مفهومی

| فیلد | الزام | توضیح |
|---|---|---|
| task_id | اجباری | شناسه یکتای Task |
| parent_task_id | اختیاری | شناسه Task والد |
| agent_type | اجباری | نوع Agent مجاز |
| objective | اجباری | هدف دقیق و قابل ارزیابی |
| tenant_id | اجباری | Tenant درخواست |
| user_id | اجباری | User درخواست |
| authorization_context | اجباری | Context مجوز معتبر و کنترل‌شده |
| input_context | اجباری | حداقل اطلاعات لازم برای انجام کار |
| expected_output_schema | اجباری | شناسه/تعریف Schema خروجی مورد انتظار |
| dependencies | اجباری | شناسه Taskهای پیش‌نیاز؛ در صورت نبود وابستگی، فهرست خالی |
| max_tool_calls | اجباری | سقف فراخوانی Tool |
| timeout_seconds | اجباری | مهلت اجرای Task |

نکات امنیتی:
- `tenant_id`، `user_id` و `authorization_context` باید از Context معتبر سمت سرور ساخته شوند.
- LLM و Agent اجازه تغییر یا ارتقای این مقادیر را ندارند.
- Agent باید در هر فراخوانی حساس، Context معتبر را به مسیر کنترل‌شده MCP منتقل کند.
- صرف وجود شناسه‌ها در مدل، جایگزین کنترل دسترسی نیست.
- از ثبت غیرضروری اطلاعات حساس در Log خودداری شود.

### 6.2 AgentResult — فیلدهای مفهومی

| فیلد | الزام | توضیح |
|---|---|---|
| task_id | اجباری | Task مربوط به نتیجه |
| agent_type | اجباری | Agent اجراکننده |
| tenant_id | اجباری | Tenant مرتبط |
| user_id | اجباری | User مرتبط |
| status | اجباری | وضعیت استاندارد مانند success، partial، failed |
| result | اجباری | خروجی ساختاریافته |
| evidence | اجباری | منابع/شواهد و شناسه‌های قابل ردیابی |
| errors | اجباری | خطاها یا هشدارها |
| execution_metrics | اجباری | زمان، تعداد Tool call و شاخص‌های اجرا |

مقادیر دقیق Enumها، محدودیت طول فیلدها، Schemaهای اختصاصی هر Agent و ساختار Evidence در سند Task Contract تفصیلی مشخص می‌شوند.

## 7. مدل اجرای Supervisor

### 7.1 چرخه اصلی

1. دریافت ورودی و Context معتبر.
2. دریافت خروجی Initial Routing و Query Understanding در صورت اجرا.
3. تعیین اینکه درخواست به Multi-Agent نیاز دارد یا خیر.
4. ساخت Plan محدود شامل Taskها و وابستگی‌ها.
5. اعتبارسنجی Plan از نظر Agent مجاز، تعداد Task، Tool و زمان.
6. اجرای Task آماده.
7. دریافت و اعتبارسنجی AgentResult.
8. به‌روزرسانی وضعیت اجرای Supervisor.
9. تصمیم‌گیری برای ادامه، تکمیل، شکست کنترل‌شده یا درخواست شفاف‌سازی.
10. ترکیب نتایج معتبر و تولید پاسخ.

### 7.2 شرط پایان

Supervisor زمانی اجرای Taskها را تمام‌شده تلقی می‌کند که:
- همه Taskهای ضروری به وضعیت نهایی رسیده باشند؛
- وابستگی حل‌نشده‌ای باقی نمانده باشد؛
- نتیجه کافی برای پاسخ وجود داشته باشد؛ یا
- ادامه اجرا به دلیل خطا، محدودیت یا ابهام متوقف شده باشد.

Supervisor باید میان `success`، `partial` و `failed` تمایز بگذارد. شکست یک Task نباید به‌صورت موفقیت کامل گزارش شود.

### 7.3 محدودیت چرخه

برای جلوگیری از حلقه بی‌پایان:
- حداکثر تعداد Task در هر درخواست محدود باشد.
- حداکثر تعداد تلاش مجدد محدود باشد.
- حداکثر Tool call برای هر Task اعمال شود.
- Timeout برای هر Task و کل درخواست اعمال شود.
- Supervisor امکان توقف کنترل‌شده داشته باشد.
- هر تصمیم برای ایجاد Task جدید قابل ثبت و ردیابی باشد.

مقادیر عددی این محدودیت‌ها در طراحی اجرایی و با توجه به رفتار واقعی سرویس تعیین می‌شوند؛ این سند عدد فرضی را قطعی نمی‌کند.

## 8. وابستگی و موازی‌سازی

موازی‌سازی براساس استقلال داده‌ای و اجرایی Taskها انجام می‌شود، نه صرفاً براساس نوع Agent.

دو Task فقط زمانی قابل اجرای هم‌زمان هستند که:
- ورودی مورد نیاز هر دو آماده باشد؛
- خروجی یکی پیش‌نیاز دیگری نباشد؛
- تداخل نوشتن یا تغییر وضعیت مشترک نداشته باشند؛
- محدودیت‌های ERP و MCP اجرای هم‌زمان را مجاز بداند.

اگر Task دوم به نتیجه Task اول نیاز دارد، اجرای ترتیبی الزامی است.

**فاز اول هیچ Parallel Execution عمومی ندارد.** ابتدا Delegation سری با یک Inventory Agent اثبات می‌شود. موازی‌سازی در فاز بعد، پس از اضافه شدن Agent دوم و Use Case مستقل، ارزیابی خواهد شد.

## 9. امنیت، مجوز و عملیات ERP

- هویت و مجوز از مسیر معتبر و موجود ERP دریافت می‌شود.
- Agentها فقط Toolهای مجاز برای حوزه و Task خود را می‌بینند.
- ورودی Toolها پیش از اجرا اعتبارسنجی می‌شود.
- عملیات نوشتن تابع کنترل قطعی، Approval و تأیید لازم است.
- خروجی LLM به‌تنهایی مجوز اجرای عملیات نیست.
- Tenant و User در زنجیره Task و Result حفظ و تطبیق داده می‌شوند.
- خطاها و رویدادهای مهم برای Audit ثبت می‌شوند.
- Agent نمی‌تواند authorization context را تغییر دهد.
- اطلاعات یک Tenant نباید وارد Context یا نتیجه Task متعلق به Tenant دیگر شود.

این سند فرض می‌کند کنترل‌های هویت و دسترسی پایه در سرویس‌های امن ERP و اجزای فعلی وجود دارند؛ هدف، حفظ و رعایت آن‌ها در مسیر Multi-Agent است، نه بازطراحی آن‌ها.

## 10. سیاست مدل و ابزار

### 10.1 جداسازی Model Policy

Supervisor و Agentها نباید مستقیماً درباره فعال‌سازی یا دور زدن سیاست مدل تصمیم بگیرند.

- انتخاب Local LLM یا OpenAI از Model Policy و Router فعلی پیروی می‌کند.
- سیاست فعلی تولید پاسخ RAG با OpenAI بدون تصمیم مستقل و تغییر مصوب، دست‌نخورده باقی می‌ماند.
- Agentها از Factory/Router موجود برای دریافت مدل استفاده می‌کنند.
- تغییر مدل باید با ارزیابی کیفیت، هزینه، زمان پاسخ و محدودیت داده انجام شود.

### 10.2 دسترسی به Tool

- دسترسی هر Agent به MCP Toolها باید محدود و صریح باشد.
- Toolهای خواندن و نوشتن باید از نظر سیاست اجرا تفکیک شوند.
- Tool call باید به Task و User/Tenant قابل ردیابی باشد.
- Agent نباید Toolهای نامرتبط را صرفاً به دلیل در دسترس بودن فراخوانی کند.

## 11. وضعیت و حافظه

در فاز اول:
- Supervisor مالک وضعیت اجرای درخواست و Taskها است.
- Agent فقط Context لازم برای مأموریت خود را دریافت می‌کند.
- AgentResult خلاصه ساختاریافته‌ای است که به Supervisor بازمی‌گردد.
- کل Conversation History به همه Agentها تزریق نمی‌شود.
- حافظه مستقل و دائمی برای هر Agent ساخته نمی‌شود، مگر آنکه Use Case و ارزیابی، ضرورت آن را نشان دهد.

وضعیت Conversation موجود در Redis/PostgreSQL یا سایر اجزای جاری، بدون دلیل و ارزیابی بازطراحی نمی‌شود. جزئیات Persistence و بازیابی اجرای نیمه‌تمام در سند Supervisor & Execution State تعیین خواهد شد.

## 12. ارزیابی و معیار پذیرش

### 12.1 Baseline

قبل از تغییر کد، مجموعه اولیه ۵۰ سؤال تهیه می‌شود:

| دسته | تعداد |
|---|---:|
| Small Talk و پرسش عمومی | ۵ |
| Document RAG | ۱۰ |
| ERP Data Query | ۱۰ |
| ERP Action | ۵ |
| Mixed Query | ۱۰ |
| Multi-step Analytical Query | ۱۰ |
| **مجموع** | **۵۰** |

برای هر سؤال باید Intent مورد انتظار، مسیر مورد انتظار، Agent/Tool مورد انتظار، شواهد مورد انتظار و معیار پذیرش ثبت شود.

یک Subset جداگانه برای ارزیابی نهایی نگهداری می‌شود و نباید در توسعه و تنظیم مکرر استفاده شود.

### 12.2 شاخص‌ها

حداقل شاخص‌های زیر ثبت شوند:
- Intent Accuracy
- Routing Accuracy
- Task Planning/Delegation Accuracy
- Agent Output Validity
- Evidence/Source Validity
- Final Answer Acceptance
- False MCP Rate
- False RAG Rate
- Latency (کل و به تفکیک مرحله)
- تعداد LLM Call و Tool Call
- نرخ خطا و Partial Completion

### 12.3 معیار عبور از فاز

در پایان هر فاز باید با همان مجموعه ارزیابی و شرایط قابل مقایسه بررسی شود:
- آیا کیفیت پاسخ بهتر شده است؟
- آیا زمان پاسخ در Use Case هدف بهتر یا قابل قبول مانده است؟
- آیا نرخ خطا یا اجرای Tool نامناسب افزایش یافته است؟
- آیا پیچیدگی و هزینه اضافه‌شده توجیه دارد؟

اگر بهبود قابل اندازه‌گیری نیست، فاز بعدی آغاز نمی‌شود تا علت مشخص و اصلاح شود. Multi-Agent بودن به‌خودی‌خود معیار موفقیت نیست.

## 13. فازبندی اجرا

### Phase 0 — Baseline
**خروجی:** دیتاست ارزیابی، نتایج پایه و گزارش خطاهای فعلی.

- تهیه و برچسب‌گذاری ۵۰ سؤال
- تعیین Subset ارزیابی نهایی
- اجرای تست‌ها روی نسخه موجود
- ثبت کیفیت، Latency، مسیر و فراخوانی ابزار

### Phase 1 — Supervisor Foundation + یک Inventory Agent
**خروجی:** یک Use Case واقعی و انتهابه‌انتها با Delegation کنترل‌شده.

- طراحی و پیاده‌سازی Task Contract و AgentResult
- تعریف حداقل State لازم برای Supervisor
- اتصال Supervisor به یک Inventory Agent
- حفظ مسیر فعلی درخواست‌های ساده
- اجرای Query Understanding فقط در مسیر پیچیده و در صورت نیاز
- عدم ساخت Registry عمومی، Runtime توزیع‌شده یا Parallel Execution عمومی

اصل محدودکننده: هر Abstraction جدید باید برای نیاز واقعی فاز اول لازم باشد. قرارداد مشترک Task از ابتدا تعریف می‌شود، اما زیرساخت عمومی فقط با وجود استفاده‌کننده واقعی ساخته می‌شود.

### Phase 2A — Sequential Delegation
**خروجی:** اثبات چرخه کامل واگذاری، اجرا، دریافت نتیجه و تصمیم Supervisor.

- تکمیل مدیریت وضعیت Task
- کنترل خطا و Timeout
- مدیریت Partial Result
- پاسخ‌سازی ساده از نتیجه Inventory Agent
- بدون موازی‌سازی

### Phase 2B — Parallel Execution
**خروجی:** اجرای هم‌زمان حداقل دو Task مستقل در یک Use Case واقعی.

- افزودن Agent دوم، برای مثال Sales، پس از انتخاب Use Case معتبر
- تعریف وابستگی‌های Task
- اجرای موازی فقط برای Taskهای مستقل
- مقایسه Latency و کیفیت با اجرای ترتیبی

### Phase 3 — Verification & Synthesis
**خروجی:** پاسخ ترکیبی با شواهد معتبر و کنترل کیفیت.

- تکمیل Deterministic Validation
- افزودن Semantic Verification در صورت اثبات نیاز
- بهبود Response Synthesis
- مدیریت تناقض و شواهد ناکافی

### Phase 4 — Controlled Expansion
**خروجی:** توسعه تدریجی براساس نتایج.

- افزودن Agentهای Production، Purchase، Finance یا سایر حوزه‌ها
- بازبینی Model Policy براساس شواهد
- بررسی حافظه اختصاصی Agentها
- بهبود بازیابی، Observability و مقیاس‌پذیری

این فاز اختیاری است و تنها در صورت ارزش عملی فازهای قبل انجام می‌شود.

## 14. ساختار کد هدف در فاز اول

ساختار زیر فقط محدوده لازم برای شروع را نشان می‌دهد و ساختار نهایی همه Agentهای آینده نیست:

```text
src/coordinator/app/
├── agents/
│   ├── query_understanding/       # موجود/پچ قبلی؛ پس از تطبیق حفظ شود
│   └── inventory/
│       ├── agent.py
│       ├── prompts.py
│       └── schemas.py
│
├── supervisor/
│   ├── state.py
│   ├── task_contracts.py
│   ├── graph.py
│   └── policies.py
│
├── graphs/
│   └── workflow.py                # مسیرهای موجود + اتصال شرطی
│
├── routing/
│   └── intent_classifier.py       # تصمیم مسیر ساده/پیچیده و مسیرهای موجود
│
├── mcp/                           # پیاده‌سازی فعلی حفظ شود
├── terminology/                   # در صورت فعال بودن، حفظ شود
└── core/                          # تنظیمات و زیرساخت موجود حفظ شود
```

در فاز اول ایجاد `agent_registry.py` عمومی، `task_dispatcher.py` عمومی، سیستم پیام‌رسانی Agent-to-Agent و پوشه‌های خالی برای همه حوزه‌ها الزامی نیست. اگر نیاز واقعی پدید آمد، ساختار در همان زمان استخراج و عمومی می‌شود.

## 15. تصمیم‌های باز برای اسناد تفصیلی

این سند تصمیم معماری سطح بالا را تثبیت می‌کند؛ جزئیات زیر در اسناد بعدی نهایی می‌شوند:

1. **Agent Task Contract:** Enum وضعیت‌ها، Schemaهای Pydantic، ساختار Evidence، محدودیت فیلدها و قرارداد خطا.
2. **Supervisor & Execution State:** State دقیق LangGraph، وضعیت Task، Retry، توقف، Resume و Persistence.
3. **Evaluation Dataset:** متن دقیق ۵۰ سؤال، داده مرجع، معیار پذیرش و روش امتیازدهی.
4. **Inventory Use Case:** انتخاب یک سناریوی واقعی و قابل تست از عملیات/گزارش‌های موجود انبار.
5. **Complexity Routing:** قواعد دقیق تشخیص مسیر ساده و پیچیده و محل اجرای Query Understanding.

## 16. معیار موفقیت معماری

این پروژه زمانی موفق است که:
- درخواست‌های ساده نسبت به وضعیت فعلی بی‌دلیل کندتر یا پیچیده‌تر نشوند؛
- درخواست منتخب Inventory از طریق Supervisor و Agent تخصصی با نتیجه قابل ارزیابی اجرا شود؛
- Tenant/User و مجوزها در تمام زنجیره حفظ شوند؛
- Taskها و نتایج ساختارمند و قابل ردیابی باشند؛
- خطا، کمبود داده و پاسخ ناقص صادقانه مدیریت شوند؛
- توسعه Agent دوم و موازی‌سازی، پس از اثبات نیاز، بدون بازنویسی اساسی امکان‌پذیر باشد؛
- بهبود کیفیت یا سرعت با ارزیابی قابل اندازه‌گیری اثبات شود.

**اصل نهایی:** Multi-Agent ابزار حل مسئله است، نه هدف محصول. معماری باید به اندازه نیاز واقعی پیچیده شود و هر قابلیت جدید باید با یک Use Case و معیار پذیرش مشخص توجیه شود.
